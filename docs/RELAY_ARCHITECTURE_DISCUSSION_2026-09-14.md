# 自部署中继与仓库结构讨论稿

状态：2026-09-14 方案已获确认并实施首版。服务、最小中继契约和双端传输已独立建项目，插件和桌面端已接入，Docker/Compose 与构建入口已提供。单仓先完成根目录产物/品牌资源整理和文档分区，原应用目录保留。实现、验证与剩余验收见 [实施记录](verification/RELAY_SETUP_2026-09-14.md)。

## 目标与连接路径

允许用户在一台双方可访问的服务器上部署 XIVChat 中继。插件和桌面端均主动向该服务建立 WSS 长连接，由服务转发数据，游戏电脑无需公网 IP、入站端口映射或 P2P 打洞。

中继本身仍需可达：跨公网使用通常部署在有公网入口的服务器上；仅有一台同样无法从外部访问的家用 NAS，并不能自动解决可达性。使用有效 TLS 证书，优先提供域名部署说明。

路径为“桌面客户端 ↔ 中继 ↔ 游戏插件”。转发的是 XIVChat 自身的聊天、卡片与截图协议，不转发游戏客户端与官方游戏服务器之间的流量。游戏及插件必须运行；角色未登录时沿用现有不可发送状态。

## 建议首版范围

- 私有实例，服务一个用户或少量受邀用户；单实例部署，支持多个独立游戏设备和每台设备的多个已授权客户端，不做公开注册平台。
- Linux 容器作为首选交付，提供固定版本镜像、Compose 示例、配置样例、初始化／签发／撤销凭据命令和升级说明。运行镜像不需要编译客户端或安装 Dalamud。
- 服务使用 ASP.NET Core WebSocket；新服务优先 .NET 10 LTS，桌面端和插件框架升级另行评估，不为引入中继强行同步升级。
- 持久化设备注册、授权凭据摘要和撤销状态，首版可用 SQLite；活动连接保存在内存。聊天、截图、历史和游戏角色资料不落中继数据库。
- 提供存活／就绪检查和最少运行指标，不暴露设备列表到匿名健康接口。首版管理通过命令及配置完成，可视化管理页后续再评估。
- 提供明确的配对、离线、连接失败、授权撤销及版本不兼容反馈。保留直连，两种连接方式由用户选择，不默默切换目标或开启另一连接。

## 用户使用流程

1. 部署者启动服务，配置 TLS、公网入口和持久目录；通过管理命令创建游戏设备注册凭据。
2. 插件填写中继地址和专属注册凭据，主动上线；管理凭据不填入插件或普通客户端。
3. 已授权插件为自己的设备请求一次性邀请，设置短有效期；可复制链接或扫码导入客户端。邀请码只是授权入口，不是设备身份或加密密钥。
4. 客户端兑换邀请，绑定独立设备凭据，首次核对插件公钥指纹并按现有流程确认设备信任。邀请过期／重用受限制，同实例的其他用户不能枚举或附着该设备。
5. 以后选择该中继连接配置即可连接；Logo 快捷连接保存连接模式、服务地址及目标设备标识，凭据使用系统安全存储，界面和日志不显示完整凭据。

注册、邀请及客户端凭据分权：签发凭据不等于已获游戏插件信任；服务授权限制“能连接谁”，端点信任校验“对端是谁”。短邀请码需严格限次；复制链接优先使用足够随机的一次性秘密，并避免进入访问日志。

## 转发与加密边界

- 服务端只理解控制消息及路由封装，对应用数据按不透明字节转发，不解析聊天正文或解密截图。TLS 保护到中继的链路，端到端加密保护插件与客户端之间的应用内容。
- 延续现有设备公钥信任，密钥变化必须明确处理。中继认证成功不能替代端点密钥校验；首次指纹核对不能仅以同一中继提供的身份声明为依据。
- 中继仍可看到连接 IP、时间、目标标识和流量大小；“不存正文”不意味着服务不知道任何连接信息。
- 原 `KeyExchange.cs`/`SecretMessage.cs` 没有通用的跨会话重放拒绝机制。本轮在透明转发流上增加端点之间的标准 TLS 1.2/1.3，由平台 TLS 处理新会话与密文序列，并固定校验插件证书指纹；内部继续保留原设备信任。详见 [Relay v1](protocol/RELAY_V1.md)，不另造密码算法，也不将自动化检查描述为完整安全审计。
- 控制协议显式携带版本、授权后的设备标识和服务生成的会话 ID，必要时携带连接轮次。每次重连生成新会话；数据到达前双方需确认会话已准备好。
- 路由依据服务器内的认证连接绑定，不能相信数据包自行声明的发送者、公钥或目标。关闭旧会话及迟到数据不得影响新会话。
- 建议插件保持一条注册控制连接，每个已授权客户端会话按需打开独立数据连接；以额外连接数量换取流控与故障隔离，避免旧实现的一条共享写队列拖慢全部设备。单客户端内截图和聊天仍需沿用端点限流及发送调度，不能声称独立连接消除了所有队头等待。
- 消息组装限制总字节数、时间和片段数量，接收缓冲区大小不等于有效的报文大小上限；每会话及每实例均限制连接数、队列条数／字节数和发送速率。
- 慢会话超限时断开并说明原因，不无限积压；中继不持久缓存离线消息，重连后复用插件游标补历史及客户端去重。
- 心跳、超时、带退避和随机抖动的重连、服务优雅退出及客户端取消都需要贯穿控制连接和数据连接。

## 现有代码复用与变化

- 可复用：MessagePack 应用协议、设备信任界面、加密帧处理的接口形态、`BaseClient`、有界队列、能力协商、补历史及角色隔离。
- 桌面端需要把 `Connection.cs` 内部 TCP 创建抽成传输接口，使直连和中继得到同一套握手／消息处理服务；保留当前直连行为。
- 插件需要可配置中继 URL、新配对流程及控制／会话生命周期。`Relay.cs` 的固定 Debug／Release 地址与单一认证码不够支撑自部署。
- 旧 `RelayConnected` 提供流适配思路，但按公钥查找会话、创建后立即转发和共享发送队列不直接照搬。另行验证握手写入何时发送，不能因缺少 Flush 造成双端等待。
- 新自部署中继采用明确的新协议版本；不默认兼容旧公共中继，也不复用旧服务凭据。旧应用协议／直连兼容与中继控制协议兼容分别说明。

## 仓库建议：先整理单仓，独立构建发布

目前约 271 个受版本管理的文件。插件和桌面端都引用 `XIVChatCommon`，桌面端还引用 `XIVChatStorage`；协议仍在共同演进，此时拆仓将引入共享包发布、跨仓版本更新和兼容联调成本。

保留一个仓库。以下是长期目标结构；本轮实际目录及独立入口见 [开发指南](development/BUILD.md)。原应用目录仍保留，不把下面的全部迁移标记为已完成：

```text
src/
  XIVChat.Plugin/
  XIVChat.Desktop/
  XIVChat.Relay/
  XIVChat.Protocol/       # 最小应用／中继协议契约
  XIVChat.Transport/      # 端点传输、握手和加密；服务端无需引用
  XIVChat.Storage/        # 桌面历史存储
tests/
  Protocol/
  Relay/
  Desktop/
  Plugin/
deploy/relay/
docs/
  user/
  development/
  protocol/
  verification/
assets/branding/
```

- 将现有 Common 中的契约与端点加密职责按实际依赖逐步分离。Relay 只依赖最小中继契约，不依赖 WinUI、Dalamud、游戏文件或桌面历史库，也不因引用 Common 带上不需要的原生加密库。
- 三端分别构建、打包、打版本和发布，记录支持的协议版本；协议变化触发跨端检查。Linux 能单独构建 Relay；Windows 专门验证桌面端与插件，游戏实测独立记录。
- 用户自部署只拉取 Relay 镜像和部署配置。源码是否在同仓不影响运行包独立。
- 整理根目录旧桌面发布 ZIP、Logo 变体、使用说明和历史验收文档；发布 ZIP 迁往版本发布附件，Logo 归入品牌资源。必要的原生 DLL 和运行时资源不能当作产物误删。不重写 Git 历史。
- 顶层桌面解决方案目前未包含插件，需提供清楚的组件构建入口。搬目录时同步项目引用、测试 targets／脚本、资源路径和构建文档，避免同时进行大规模业务改写。
- 建议先做构建入口和文档整理，再小批量迁移目录，每批验证受影响构建；不靠一次性移动整个仓库完成重构。

等到独立维护团队／权限隔离成为实际需求，或中继协议稳定且服务端发布明显独立时，再优先考虑将 Relay 拆出。此时先把协议契约做成有版本的共享包，建立跨版本联调，再迁移仓库；无需一开始就拆成三个仓库。

## 开发与验收顺序建议

1. 收敛首版范围，明确注册／邀请／信任模型、加密会话边界和协议文档。
2. 建立独立 Relay 构建与测试入口；完成一插件、一客户端的本地端到端闭环，桌面端和插件同步接入。
3. 加入多设备会话隔离、撤销、服务重启、限流、截图和故障恢复测试。
4. 容器、TLS、持久化及升级流程完成后，用真实不同网络验证纯中继路径；禁用直连路径，确认没有依靠局域网连接让测试误通过。
5. 验证聊天双向收发、历史补拉、好友／卡片／截图、多窗口、角色隔离及断线提示；记录延迟、流量和资源边界后发布。

网络首版需明确服务器流量成本：每份数据由中继接收再转发，服务端出口与转发量相应增长；截图通常比文本更占带宽。中继暂时不可用时两端仍可查本地历史，但不能经中继实时收发。
